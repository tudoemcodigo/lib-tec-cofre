## ⚠️ Riscos residuais (conhecidos e aceitos)

| Risco | Motivo | Mitigação recomendada |
|---|---|---|
| **Purge liberado na API** | Decisão de projeto (operações destrutivas sem trava no componente) | Ativar *purge protection* no cofre de produção; papéis *Officer* só para quem precisa; alertas no log de auditoria para `*.purge` |
| Valor como `string` na memória gerenciada | O SDK do Azure expõe `string`; não é possível zerar | Não guardar `VaultSecret` além do uso; preferir `IKeyCryptography` (a chave não sai do cofre) a segredos quando possível |
| `IConfiguration` mantém valores em memória a vida toda | Natureza do `IConfiguration` | Usá-lo para configuração; ler segredos de alto valor sob demanda |
| Cache serve valor sem auditoria e após revogação de acesso | Troca consciente por latência | Deixar desligado (padrão) ou usar duração curta |
| Valor expirado do cache continua na memória enquanto não houver novas leituras | O `MemoryCache` só varre os expirados quando é acessado (não há timer próprio: um timer manteria o cache vivo e seria mais um ponto de falha). O valor expirado **nunca** é servido; só não é liberado antes do próximo acesso, do descarte do cache ou do fim do processo | Duração curta; com tráfego de leituras a varredura ocorre no máximo a cada minuto (ou a cada duração, se menor) |
| Escrita pela classe concreta do provedor não limpa o cache | Com `EnableSecretCache`, a classe concreta (ex.: `AzureKeyVaultSecretStore`) continua registrada no container (contrato do `UseSecretStore`: provedores e aplicações a resolvem) e não passa pelos decorators | Gravar sempre por `ISecretStore`/`ISecretRecycleBin`/`ISecretBackup`; injetar a classe concreta só para leitura sem cache |
| Nomes e tags aparecem em log/listagens | Necessário para auditoria | Nunca colocar dados pessoais em nomes/tags |
| `EphemeralKeySet` no Windows não funciona com `SslStream` como servidor | Limitação do SChannel | Para TLS de servidor, usar o certificado via Kestrel/App Service, não o download |
| `CryptographyClient` busca a chave pública na primeira operação de cada cliente (operações públicas locais) | Comportamento do SDK; o cliente é reaproveitado por nome + versão (até 256, por no máximo `CryptographyClientLifetime`), mas sem versão é recriado a cada chamada para seguir rotações | Dá à identidade também `keys/get` (incluso em *Crypto User*); informe a versão quando possível |
| Revogação de chave não é imediata para encrypt/wrap/verify | Essas operações são locais (chave pública em cache no cliente do SDK). Desabilitar, expirar ou excluir a chave vale **na hora** para decrypt, unwrap e sign (sempre remotos) e em até `CryptographyClientLifetime` (padrão 10 minutos) para encrypt, wrap e verify com versão informada | Reduzir `CryptographyClientLifetime` (mínimo 1 minuto) onde a revogação rápida importa; dados cifrados nesse intervalo continuam protegidos (só quem tem decrypt os lê) |
| Instrumentação de `HttpClient` de terceiros grava `url.full` com o endereço do cofre e o nome/versão do item | Fora do controle do componente (#29): ele só desliga os spans do próprio SDK | O TEC.Observability já exclui os hosts de Key Vault do rastreamento HTTP; em outra pilha, filtrar `*.vault.azure.net`, `*.vault.azure.cn` e `*.vault.usgovcloudapi.net` |
| Chave privada de certificado em `string`/objetos imutáveis durante a importação | Os buffers da biblioteca são zerados (#37), mas restam: a senha (`ImportCertificateOptions.Password`, `string`), o corpo da requisição montado pelo SDK do Azure (Base64 do conteúdo), o array do chamador e as cópias internas do `X509Certificate2` | Descartar o array de origem após importar (`CryptographicOperations.ZeroMemory`); preferir criar o certificado no cofre (`CreateCertificateAsync`) a importar |
| `DefaultKeySet` no macOS | `EphemeralKeySet` não existe no macOS | Em macOS, prefira `IKeyCryptography` (a chave não sai do cofre) ao download do certificado |
| Leitura compartilhada do cache continua após o cancelamento do chamador | Coalescência: o cancelamento de um chamador não pode cancelar os demais | Limitada pelos timeouts do provedor (`NetworkTimeout`, `MaxRetries`) |
| Segredo gerenciado (com chave privada) legível por `ISecretReader` | Decisão de projeto: um cofre por aplicação, papéis RBAC definem o acesso | Auditoria em `Information`; alertas para leituras de segredos gerenciados; não dar *Secrets User* a quem só precisa assinar (use `IKeyCryptography`) |
| Rotação de segredo não é atômica | Gravar a nova versão e desabilitar as anteriores são chamadas separadas | `RotateSecretAsync` retorna `SecretRotationResult` com a versão criada; concluir com `DisablePreviousSecretVersionsAsync` (idempotente) |
| No .NET 8, PFX carregado pelo construtor de `X509Certificate2` (sem os `Pkcs12LoaderLimits` do `X509CertificateLoader`) | `X509CertificateLoader` só existe no .NET 9+; decisão de não adicionar dependência (`Microsoft.Bcl.Cryptography`) | Tipo de conteúdo conferido antes, tamanho limitado a 1 MB antes da carga, senha conferida; em .NET 8 mantenha o runtime atualizado (os limites de iteração do PKCS#12 vêm em atualizações de segurança) ou prefira .NET 10 |
| Dois avisos de trimming/AOT do `Azure.Core` (`LightweightPkcs8Decoder`, `IL2026`/`IL2075`) | Código interno do SDK (1.53 a 1.63), fora do controle do componente; usado só para chaves EC em PEM de credenciais por certificado | Usar `ManagedIdentity`/`WorkloadIdentity`/`Developer` (não passam por esse caminho); com credencial por certificado EC em AOT, testar a aplicação publicada |
| Provedor em memória guarda chaves privadas em memória do processo, sem HSM | Natureza do provedor de desenvolvimento | Trava de Development (#28); nunca usar dados reais |

## ✅ Checklist do Key Vault

Configurações recomendadas no `kv-tec-base` e, obrigatoriamente, nos cofres de produção:

- [ ] **Modelo de permissão RBAC** (não *access policies*), com papéis atribuídos por identidade e no menor escopo possível.
- [ ] **Soft delete** com retenção de 90 dias e **purge protection** ativada (produção).
- [ ] **Acesso de rede restrito**: *private endpoint* ou firewall com *selected networks*; acesso público desabilitado em produção.
- [ ] **Configurações de diagnóstico** enviando `AuditEvent` ao Log Analytics, com alertas para `SecretPurge`, `KeyPurge`, `CertificatePurge` e falhas 403 repetidas.
- [ ] **Microsoft Defender for Key Vault** habilitado.
- [ ] Um cofre por aplicação e ambiente (não compartilhar produção com testes).

## 🔗 Cadeia de suprimentos

Mesmo padrão do TEC.Core e TEC.Cqrs: analisadores de segurança como erro, analisadores de trimming/AOT (IL2xxx/IL3xxx) como erro em todos os pacotes, `EnablePackageValidation` (mesma API em `net8.0` e `net10.0`), `NuGetAudit` (inclusive transitivos) com `NU1901`–`NU1904` como **erro** em todos os projetos (inclusive testes), `packages.lock.json` em todos os projetos (inclusive testes) com restore `--locked-mode`, `packageSourceMapping` (`TEC.*` só do feed interno), SDK fixado em `global.json`, build determinístico e SourceLink. No GitHub Actions, todas as actions são fixadas por SHA de commit (com a tag em comentário) e o CodeQL (`security-and-quality`) analisa o C# em PRs, na `main` e semanalmente. O pacote `TEC.Cofre` não depende de SDK de nuvem: quem usa outro provedor não carrega o SDK do Azure; o provedor em memória fica num pacote próprio (`TEC.Cofre.InMemory`), fora da aplicação de produção. O CI instala o SDK do `global.json` e o runtime 8.0 e roda todos os testes nos dois alvos.
